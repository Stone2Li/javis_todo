# 第二轮平台调研：购买验证、鸿蒙网络与安全存储

日期：2026-11-06。结论基于本轮实际读取的官方源码和文档；没有进行真机验证、创建商店商品或调用收费服务。

## 1. 网络复查结果

用户告知已开放网站策略后，本轮重新读取当前实例状态、配置草稿并发起真实 HTTPS 请求：

| 层次 | 本轮观察 |
|---|---|
| 配置草稿 | revision 2，已保存 developer.apple.com、developer.huawei.com、docs.flutter.dev、reactnative.dev、kotlinlang.org、platform.openai.com 六个自定义域名 |

## 2. iOS：付费 App 证明与试用身份有了具体实现候选

核验源码：Apple 官方 `app-store-server-library-node`，固定提交 `b71d9c70aa4a4a5efea258d530f50733a7916af3`。该快照 package.json 为3.1.0，README写明Node22+；不据此宣称这是已发布的最新npm版本。

### 已确认的接口与边界

1. `SignedDataVerifier.verifyAndDecodeAppTransaction(signedAppTransaction)` 专门处理签名AppTransaction，校验app标识与环境。生产环境检查bundleId/appAppleId，并走证书链和签名验证。[R1][R2]
2. 模型字段包括 `appTransactionId`、`receiptType`、`originalPurchaseDate`、`originalApplicationVersion`、`deviceVerification`、`deviceVerificationNonce`。字段在模型中是可选值；不能要求所有历史设备、系统和凭证必然携带它们。[R1]
3. 当前库还定义 `getAppTransactionInfo(anyTransactionId)`，可接受属于该用户/应用的transactionId、originalTransactionId或appTransactionId，返回签名应用交易信息。这只是已确认的服务端接口，生产访问资格、权限、限额和本产品可用性仍需实际验证。[R3]
4. `Environment.XCODE` / `LOCAL_TESTING` 在底层明确跳过App Store签名验证。这是本地测试路径，不能用此环境向生产用户发放托管试用。必须由服务器配置环境，不能让客户端选择验证级别。[R2]
5. `AppTransaction` 模型本身未列出 `revocationDate`。不能把内购交易的撤销字段机械用于付费App下载，也不能推断付费App永远无法感知退款；实际撤销/退款信号仍待商业文档与平台测试确认。[R1]

### 对 M09/M10 的设计修订

- iOS主候选：客户端获取经过系统验证的应用购买证明 → 服务端官方验签器验证 → 归一化VerifiedAppPurchase → 绑定内部匿名主体 → 发放试用令牌。基础本地功能与Hosted身份分离。
- 归一化结构至少有 platform、storeEnvironment、appIdentity、evidenceKind、verificationStatus、verifiedAt；canonicalStoreSubject、originalPurchaseAt可为空。不要把完整JWS放普通日志。
- 在实测证明标识满足重装与跨设备预期后，可使用 `(platform, environment, appIdentity, appTransactionId)` 作为商店主体候选唯一键。数据库内部映射可做带版本的HMAC去标识化；仍属于可关联数据，需保留/删除策略。不能用完整JWS的hash当购买身份，因为签发时间和设备相关字段可改变。
- 服务端字段模型只证明“存在下载交易标识”，**没有证明它在换设备、重装、家庭共享、换Apple账户时如何变化**，也没有证明候选iOS17客户端能直接读到所有新增字段。这些都列入 G2，缺字段时不拼接日期假造身份。
- 有效签名不是调用者当前拥有此购买的完整证明。复制他人的真实JWS仍需考虑重放/主体绑定；普通challenge并不能让一个原本不含challenge的签名载荷自动具备绑定关系。是否采用App Attest等额外校验，须单独验证覆盖率、隐私与失败策略。
- 购买证据没有直接给出本次支付金额；若应用曾免费、促销、迁移或家庭共享，需要产品定义哪些购买历史属于基础版和试用资格。不能仅凭 `originalPurchaseDate` 非空就声称收到¥3。
- 计时继续使用Hosted首次成功的服务端时间，而非originalPurchaseDate或receiptCreationDate。刷新证明不重置72h，创建新installationId也不发第二份预算。

### iOS新增验证用例

| 场景 | 应验证的结果 |
|---|---|
| 篡改/错误bundleId/appAppleId/环境 | 不发Hosted权益；记录分类错误，不输出原始敏感载荷 |
| Xcode/Local Testing载荷送生产 | 被生产验签配置拒绝，绝不能以本地测试成功作为生产证据 |
| 同购买多次刷新JWS | 映射同一主体，首次成功时间与预算不重置 |
| appTransactionId缺失 | 明确进入待验证/替代识别路径，不生成假标识 |
| 重装/第二设备/家庭共享/换账户 | 记录真实字段与权益结果，未测不宣称防重领已解决 |
| 合法JWS被另一安装复制 | 验证重放防护与额度隔离方案，不能只看签名有效 |
| 免费历史/促销/退款 | 按已确认商店规则与产品政策处理，不推断支付金额 |

## 3. HarmonyOS：BYOK流式请求具备开源API依据

固定OpenHarmony文档提交 `f41b9345badd47c7ab0c263344cd7f4b5a549afb`。[R4]

已确认：`requestInStream` 在文档标为API10+，要求 `ohos.permission.INTERNET`，返回值为HTTP状态码；响应字节通过 `on('dataReceive')` 的ArrayBuffer获得，`on('dataEnd')`表示响应接收结束。`destroy()`用于终止请求并释放系统资源。原子服务标注的更高API要求，不等于普通应用必须提高最低版本。

实现由此拆为：原生HTTP transport → 增量UTF-8解码 → SSE事件拼包 → Provider协议解析 → Schema验证。不要把返回的HTTP状态码当模型文本，不要把一次dataReceive回调当作完整JSON或完整SSE事件；`dataEnd`也不自动表示已拿到有效业务结果。

M05至少新增以下fixture：

- 中文字符跨字节分包、一个事件被分到三段、多个事件合在一段、CRLF与空行、Provider错误事件、无终止标记的EOF。
- 点击取消后destroy并清理监听/缓存，晚到回调不更新已关闭页面；取消不等于Provider必定未产生费用。
- 超时/429/证书失败可解释，关闭TLS验证不是回退方案；更换origin不得携带旧Key，拒绝不安全重定向。

这些是OpenHarmony技术依据；商业HarmonyOS选定SDK、设备SystemCapability与目标API仍需比对和真机验证。没有据此确认商业ASR、IAP或实况窗。

## 4. HarmonyOS：密钥字段和录音生命周期的新增约束

### 4.1 Asset Store Kit

新增资产官方文档明确：[R5]

- `SECRET` 是敏感明文输入字段，Uint8Array长度 **1–1024字节（包含端点）**。
- `ALIAS`和`DATA_LABEL*`自定义属性不加密，不能存Key或个人敏感信息。
- ALIAS长度为1–256字节，适合保存随机引用；服务商显示名称等非秘密元信息可在普通配置库保存。

修订SecretStore：按UTF-8编码后的字节数校验；SECRET存Key，随机alias作为keyRef。超长Key采用HUKS管理加密密钥+加密文件方案，禁止截断Key、把Key转存ALIAS或为了凑长度拆成明文标签。Key写入失败不能显示配置成功。

新增测试：SECRET为0/1/1024/1025字节、Unicode字符字节长度、更新/删除/读取失败、锁屏不可访问、日志和备份扫描。最终上限按商用SDK版本复核。

### 4.2 AudioCapturer

OpenHarmony官方录音文档要求麦克风类音源具备 `ohos.permission.MICROPHONE`，提供stateChange状态监听，并要求按状态转换调用接口、完成后release资源。[R6]

把M07拆成两个可单验包：

1. **CaptureSession**：权限→录音→停止/取消→文件/资源清理；不依赖ASR或LLM。验收时检查录音指示、权限撤销、重复start/stop、页面退出与重入。
2. **SpeechTranscriber**：音频/系统会话→可编辑转写→错误恢复；能力由商用Speech SDK、模型、语言、设备和网络共同决定。

系统录音源名称中含VOICE_RECOGNITION不等于提供语音转文字模型。录音成功也不能代替PRD语音捕获验收。当前商业ASR的语言、离线、费用及支持版本仍未核实。

## 5. 开发顺序调整

总架构与粗排期维持原案，但M00/M05/M07/M09增加明确子门禁，不把待验证项算作已完成：

| 子包 | 可独立交付 | 不依赖/仍依赖 |
|---|---|---|
| M05a 原生流式transport | fake SSE服务完成解析/取消/错误测试 | 不依赖真实模型；最终依赖商用SDK真机 |
| M05b SecretStore | 边界长度、无秘密标签、读写删、锁屏与导出检查 | 不依赖LLM；最终依赖系统安全存储 |
| M07a CaptureSession | 双端录音与生命周期演示 | 不依赖ASR；不算完成语音转任务 |
| M07b 系统ASR | 固定音频→编辑转写；能力探测与降级 | 依赖实际Speech SDK与设备 |
| M09a iOS应用购买证明 | 官方验签器集成、环境隔离、归一化结果 | fake载荷只测接口，正式通过需商店证据 |
| M09b Harmony购买适配 | 商业商品/凭证/恢复/撤销证据 | 目前依赖商业文档与后台，尚阻塞 |
| M09c 商店主体映射 | 刷新/重装/跨设备/缺字段/重放的权益测试 | 依赖M09a/b，不以mock证明稳定标识 |

政策门禁不变：本轮没有拿到最新版BYOK审核规则、两商店实际¥3价格、付费App退款完整处理链或商业ASR说明，因此不作“已可上架”的结论。
