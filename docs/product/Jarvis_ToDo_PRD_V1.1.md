# 1. 产品概述

## 1.1 产品背景

传统 Todo
应用主要解决任务记录、分类、提醒和勾选完成等问题。用户仍然需要自行判断任务执行顺序、拆解复杂目标、管理任务上下文、记录阶段性成果，并在每天结束时重新整理未完成事项。

当任务数量增加、项目并行时，任务管理本身可能成为额外负担。用户经常面临以下问题：

-   有很多待办事项，但不知道当前最适合从哪一件开始。
-   复杂任务缺少明确的第一步，容易被拖延。
-   在不同任务和项目之间频繁切换，难以保持连续投入。
-   任务做了一半后中断，重新开始时需要花时间回忆上下文。
-   工作过程、临时想法和最终成果分散在不同应用中。
-   每天需要手动判断哪些任务已经完成、哪些应该延期。
-   许多 AI 工具采用持续订阅制，用户不希望为了偶尔使用 AI
    而承担固定月费。

随着大语言模型、语音识别和智能体技术的发展，任务管理可以从"记录任务"进一步升级为"理解任务、组织行动、保留上下文和辅助复盘"。

Jarvis ToDo 希望通过
AI，将任务捕获、任务规划、执行记录和每日复盘整合为一个连续的个人工作流，并通过低价买断和
BYOK 降低长期使用门槛。

## 1.2 产品定位

Jarvis ToDo 是一款移动端优先的 AI Native
个人效率工具。它不仅帮助用户记录"要做什么"，还帮助用户判断"现在如何开始、接下来如何持续，以及下次如何继续"。

**核心定位：Your Personal Flow Assistant.**

## 1.3 产品愿景

让用户减少花在管理任务上的时间，把更多注意力投入真正重要的工作。

## 1.4 产品设计原则

1.  **Flow First：**
    任务组织以降低启动成本、保持上下文连续性和匹配当前精力为目标，不等同于传统重要性排序。
2.  **Voice First：** 语音是重要输入方式，但文字输入始终可用。
3.  **Minimalism：** 视觉参考 Typora 的简洁文档体验和 Obsidian
    的信息组织方式，避免复杂 Dashboard。
4.  **Task Memory：** 每个任务都能沉淀笔记、工作日志、成果和复盘。
5.  **AI Native：** AI
    能力贯穿捕获、理解、规划、执行和复盘，而不是仅提供独立聊天窗口。
6.  **Human in Control：** AI
    提供建议和草稿；关键状态变更、计划确认和数据删除由用户控制。
7.  **Privacy First：**
    语音、笔记、附件和工作记录属于个人数据，应提供清晰的权限、保留和删除机制。
8.  **Local-first：** 基础任务和笔记优先保存在本地，AI
    服务不可用时仍可使用核心功能。
9.  **No Forced Subscription：** 用户一次购买后永久使用基础功能；AI
    托管体验结束后可自行选择 BYOK，不自动续费。

# 2. 产品目标与非目标

## 2.1 产品目标

### G1：降低任务捕获成本

用户可以通过自然语言语音或文字快速记录一个或多个任务，减少手动填写字段的负担。

### G2：帮助用户更容易进入工作状态

AI
根据任务启动成本、上下文连续性、精力匹配、任务清晰度、切换成本和时间约束，生成可解释、可调整的执行建议。

### G3：保留任务过程与上下文

每个任务可以关联 Notes、Work Logs、Results 和
Reflection，使用户中断后能够快速恢复工作。

### G4：建立每日复盘闭环

用户通过晚间语音复盘总结工作，AI
识别任务进度、成果、阻塞因素，并生成次日计划建议。

### G5：降低 AI 使用门槛和长期成本

用户以一次性低价购买软件，获得基础功能永久使用权，并可通过 72 小时托管
AI 体验了解产品价值。体验结束后，用户可以配置自己的 API Key 继续使用
AI。

### G6：适配 iOS 与 HarmonyOS

核心产品体验和业务数据模型尽可能保持一致；Widget、服务卡片、快捷操作等系统能力按平台分别适配。

## 2.2 非目标（V1 不做）

-   团队协作、多人任务分配和复杂权限管理。
-   企业级项目管理、甘特图和资源排期。
-   默认持续监听麦克风。
-   无需用户确认就自动删除任务、覆盖笔记或认定任务完成。
-   第一版即实现复杂的端侧大模型或完全离线 AI Agent。
-   强制月度或年度订阅。
-   由 Jarvis 无限补贴用户的第三方模型调用成本。
-   V1
    不承诺提供自建云同步、无限云端文件存储或跨设备实时同步；相关能力需单独规划和评估成本。

# 3. 目标用户与使用场景

## 3.1 目标用户

  ----------------------------------------------------------------------------------------------
  用户群体                 典型需求                             主要价值
  ------------------------ ------------------------------------ --------------------------------
  学生、研究人员           管理研究任务、文献、实验、论文进度   任务拆解、过程记录、成果沉淀

  程序员、AI 工程师        并行管理项目、开发任务和问题         上下文恢复、连续专注、工作日志

  产品经理、知识工作者     管理会议、文档、沟通和长期项目       语音捕获、任务组织、每日复盘

  自由职业者、独立开发者   管理个人项目和交付事项               项目视图、任务计划、成果归档

  普通个人用户             管理工作与生活中的事项               快速记录、提醒和轻量规划
  ----------------------------------------------------------------------------------------------

## 3.2 核心使用场景

### 场景 A：临时想到任务

用户说："明天下午之前完成项目报告，今天先整理数据，再写结果部分。"\
系统识别多个任务、时间约束和任务依赖，生成待确认任务。

### 场景 B：开始一天的工作

用户打开 Today 页面。Jarvis
根据已有任务、可用时间和用户当前状态，建议一个 Warm-up
行动和后续核心任务。

### 场景 C：中断后恢复任务

用户打开昨天进行中的任务。Jarvis
汇总上次完成内容、未解决问题和下一步行动，帮助用户继续工作。

### 场景 D：记录工作进度

用户在任务详情页说："刚才完成了数据清洗，发现两个变量有缺失值。"\
系统将内容保存为该任务的一条 Work Log，而不是默认创建新 Todo。

### 场景 E：晚上复盘

用户口述当天工作。AI
提取完成事项、进行中事项、阻塞因素和新增任务，生成次日计划草稿，用户确认后生效。

### 场景 F：AI 试用结束后继续使用

用户完成三天托管 AI 体验后，可以配置自己的 API Key 继续使用
AI，也可以不配置 API Key，继续永久使用基础功能。用户不会因 AI
体验结束而失去任务、笔记、日志、成果或历史记录。

## 4.4 72 小时 AI 体验规则

### 试用开始条件

-   试用不从 App 购买时间或安装时间开始。
-   用户首次成功调用 Jarvis 托管 AI 时开始计时。
-   试用时长为连续 72 小时。
-   用户首次使用 BYOK 时，不自动消耗托管 AI 体验时间。
-   用户可以先配置自己的 API Key，也可以之后再使用托管 AI 体验。

### 试用状态

  状态          含义
  ------------- -------------------
  NOT_STARTED   尚未开始 AI 体验
  ACTIVE        72 小时体验进行中
  EXPIRED       体验时间已结束

AI 使用方式另行记录： - HOSTED：Jarvis 托管 AI。 - BYOK：用户自己的
Provider。 - NONE：暂不使用 AI。

### 试用额度

为控制成本，72
小时体验还需要设置合理的总预算和频率限制，具体额度由运营配置，不在客户端硬编码。

建议控制： - 单用户总 Token 或成本预算。 - 每分钟和每日请求频率。 -
单次输入长度和附件大小。 - 超出额度时的友好提示。

当试用额度提前用完时： - 明确告知用户额度已用完。 - 不继续产生托管 AI
费用。 - 提供配置 BYOK 的入口。 - 基础功能继续可用。

当 72 小时结束时： - 托管 AI 自动停止。 - 不自动扣费。 -
不自动切换到其他付费服务。 - 用户可配置 BYOK 继续使用 AI。 - 已有 AI
生成内容和任务数据继续保留。

### 试用身份与防滥用

需要在隐私合规前提下防止通过反复卸载和重装无限领取试用。

建议优先使用应用商店购买凭证和可选账户体系管理权益。若需要账户识别，应清晰告知用户用途，并遵循平台隐私要求。

不得使用隐蔽设备指纹追踪用户。

## 4.5 BYOK（Bring Your Own Key）

用户可配置自己的模型服务商 API Key，由用户直接承担模型服务商产生的费用。

### BYOK 支持范围

V1 建议支持： - OpenAI API。 - OpenAI-compatible API。

后续根据用户需求增加其他服务商适配。

"OpenAI-compatible"不代表所有供应商完全兼容。不同服务商可能在鉴权、模型名称、接口路径、结构化输出、工具调用和上下文长度方面存在差异，需要通过
Provider Adapter 适配。

### 配置字段

  字段                    必填 说明
  -------------- ------------- --------------------------
  Provider                  是 服务商类型
  API Base URL     视 Provider 自定义兼容服务地址
  API Key                   是 用户自己的密钥
  Model ID                  是 用户选择或填写的模型名称
  API 参数                  否 兼容服务商的可选配置

### BYOK 交互流程

1.  用户打开 Settings → AI Provider。
2.  选择 Provider。
3.  填写 API Base URL（如适用）。
4.  输入 API Key。
5.  填写或选择 Model ID。
6.  点击 Test Connection。
7.  系统执行最小化连接测试。
8.  测试成功后，用户选择启用该 Provider。
9.  后续 AI 请求使用该配置。

### BYOK 费用说明

配置页面必须明确说明： - API Key 来自第三方服务商。 -
模型调用费用由服务商直接向用户收取。 - Jarvis 不收取额外 AI 订阅费。 -
实际费用、模型限额和数据处理政策以服务商为准。 - 用户应自行保护 API
Key。

### BYOK 安全要求

-   iOS 使用 Keychain 保存 API Key。
-   HarmonyOS 使用对应系统安全存储能力。
-   API Key 不进入普通任务数据库。
-   默认不将 API Key 上传至 Jarvis 服务器。
-   默认不通过 Jarvis 自有代理转发 BYOK 请求。
-   API Key 不得出现在日志、崩溃报告、分析事件或导出文件中。
-   用户可以查看已配置 Provider、测试连接、切换 Provider 和删除 Key。
-   不默认跨设备同步 API Key。
-   设备安全存储不能被描述为绝对不可提取；需在隐私说明中披露合理风险。

### BYOK 网络与模型适配

-   客户端通过 Provider Adapter 直接调用用户配置的服务商。
-   请求前校验配置完整性。
-   对鉴权失败、余额不足、模型不存在、网络错误、速率限制等提供明确提示。
-   对不支持结构化输出的模型提供兼容回退方案。
-   对不支持工具调用的模型，相关 Agent
    功能应采用文本结构化流程或提示用户功能受限。
-   用户切换 Provider 后，已有任务和 AI 生成内容不受影响。

## 4.6 ASR 与 LLM 成本边界

语音识别和大语言模型调用是不同能力，必须在产品和技术上分开设计。

-   ASR：将语音转换为文字。
-   LLM：理解任务、拆解任务、生成 Flow Plan 和复盘。

V1 建议优先使用系统语音识别能力完成转写，再将文本交给托管 AI
或用户自己的 LLM API。

若某平台或设备无法提供可用的系统语音识别，则应提供替代方案，并明确说明是否会产生第三方服务费用。

BYOK 不自动代表 ASR
免费。任何额外的云端语音识别费用都必须在使用前向用户说明。

## 4.7 平台支付与审核要求

-   iOS：使用 Apple 允许的 App
    分发和数字功能支付机制；具体买断、试用权益和应用内功能解锁方案需按当前

-   不得在未确认平台政策前假设两端支付流程完全一致。

-   退款、撤销购买和权益恢复必须遵循平台凭证状态。

# 6. 功能需求

## 6.1 模块 A：Smart Capture（智能捕获）

**需求优先级：P0**

### A-01 多方式输入

支持： - 语音输入。 - 文字输入。 - 快速创建单个 Todo。 -
从任务详情添加笔记或进度记录。

后续可扩展图片、文件和链接输入。

### A-02 语音转写

用户主动点击录音入口后开始录音，结束后生成转写文本。用户可以在提交前查看和修改转写结果。

要求： - 展示录音状态和录音时长。 - 支持取消、结束和重新录制。 -
网络或识别失败时保留可恢复的输入内容。 -
未经用户明确操作，不进行持续麦克风监听。 -
明确告知录音和转写数据的处理方式。 - 优先使用系统 ASR；若使用第三方
ASR，明确服务商和费用边界。

### A-03 自然语言任务提取

AI 从用户输入中识别： - 任务标题。 - 任务描述。 -
所属项目（若可判断）。 - 截止时间。 - 预计耗时（若可合理推断）。 -
任务依赖。 - 预期结果或完成标准。 - 输入意图类型。

意图类型至少包括： - CREATE_TASK：创建任务。 - UPDATE_TASK：修改任务。 -
DELETE_TASK：删除任务请求。 - ADD_NOTE：添加笔记。 -
LOG_PROGRESS：记录进度。 - ADD_RESULT：记录成果。 - REVIEW：复盘。 -
UNKNOWN：无法可靠判断。

### A-04 多任务提取

一段输入可以识别出多个任务。系统应展示结构化结果，允许用户逐项修改、删除或确认。

### A-05 时间识别规则

-   明确日期和时间优先使用用户原话。
-   "明天""下周三"等相对日期需根据用户设备时区解析。
-   只说"尽快""有空时"等模糊时间时，不得自动生成精确截止时间。
-   AI 推断的日期必须标注为建议或待确认。
-   保存原始表达和标准化时间值，便于用户核对。

### A-06 Inbox

新捕获但尚未整理的任务进入 Inbox。用户可以： - 确认任务。 - 编辑字段。 -
关联 Project。 - 要求 AI 拆解。 - 合并重复任务。 - 删除任务。

### A-07 意图冲突处理

如果系统无法判断用户是在添加任务、补充笔记还是记录进度，应询问用户，不得默认创建任务。

**验收标准：** 1. 一段语音可以识别出多个独立任务。 2.
用户能在保存前编辑识别结果。 3. 系统能区分任务创建、任务进度和笔记输入。
4. 模糊日期不会被伪装成明确截止时间。 5. AI
服务失败时，原始输入不会丢失。

## 6.2 模块 B：Flow Scheduling（面向心流的任务组织）

**需求优先级：P0；个性化学习为 P1**

### B-01 产品目标

Flow Scheduling
不以传统优先级分数作为唯一排序依据，而是寻找更容易开始、能够保持上下文连续、符合当前精力并能持续推进的任务顺序。

核心问题：

> 考虑用户当前状态、可用时间和任务上下文，下一步采取什么行动最有利于用户开始并持续投入？

### B-02 任务评估维度

  ---------------------------------------------------------------------------------------
  维度                    定义                                   主要用途
  ----------------------- -------------------------------------- ------------------------
  Startability            任务启动成本和第一步是否明确           选择
                                                                 Warm-up、降低启动阻力

  Context Continuity      与当前任务或项目上下文的连续程度       减少上下文切换

  Energy Fit              任务认知负荷与用户当前精力的匹配程度   选择适合当前状态的任务

  Challenge-Skill Fit     任务挑战与用户能力的匹配程度           避免过难或过于无挑战

  Switching Cost          切换任务、工具或项目的成本             控制频繁切换

  Task Clarity            目标、完成标准和下一步是否清楚         必要时先拆解任务

  Time Constraint         截止时间及延迟成本                     作为调度约束

  Dependency              是否为其他任务的前置条件               避免错误执行顺序
  ---------------------------------------------------------------------------------------

### B-03 Flow Plan 阶段

默认提供四种任务阶段，实际安排可根据用户日程调整：

**Stage 1 --- Warm-up** - 建议时长：5--15 分钟。 -
选择启动成本较低、且最好与后续核心任务有关的行动。 -
目标是帮助用户开始，而不是用简单杂事填满时间。

**Stage 2 --- Deep Work** - 初始建议时长：45--90 分钟。 -
安排适合连续投入的核心任务。 - 尽量避免无必要的任务切换。 - 支持进入
Focus Mode。

**Stage 3 --- Batch Work** -
集中处理邮件、沟通、行政和低认知负荷任务。 -
减少零散任务对深度工作的干扰。

**Stage 4 --- Wrap-up** - 保存工作成果。 - 更新任务状态。 -
记录遗留问题和下一步行动。 - 为下次恢复工作保留上下文。

以上时间是初始产品默认值，不是固定规则。用户可以调整，AI
可根据实际使用数据提出个性化建议。

### B-04 Daily Plan 生成

输入信息： - 用户已确认的任务。 - 截止时间。 - 任务依赖关系。 -
任务预计耗时。 - 用户可用时间。 - 用户主动报告的当前精力状态（如有）。 -
最近任务上下文。 - 用户历史计划接受和修改记录。

输出信息： - 推荐任务顺序。 - 每项任务所属阶段。 -
建议开始时间或时间段（仅在信息足够时生成）。 - 预计时长。 - 推荐理由。 -
不确定因素和待确认事项。

### B-05 计划控制

用户可以： - 接受整个计划。 - 调整任务顺序。 - 锁定任务。 - 推迟任务。 -
修改可用时间。 - 修改当前精力状态。 - 删除计划中的任务，但不删除原始
Todo。

AI 不得无故覆盖用户已确认或锁定的计划。计划更新时应展示变更内容和原因。

### B-06 个性化工作画像

后续根据用户主动反馈和实际使用数据学习： - 不同时间段的工作偏好。 -
各类任务的预计耗时与实际耗时差异。 - 用户常推迟的任务类型。 -
用户偏好的专注时长。 - 用户常见的项目切换模式。 -
用户对推荐顺序的接受或修改情况。

用户应能够查看、修改或重置个性化偏好。

### B-07 规则约束

-   不得为了降低启动成本而持续推迟重要或有截止时间的任务。
-   任务依赖必须满足后才能推荐执行。
-   可用时间不足时，应建议拆分、延期或调整，不得假设用户能完成全部任务。
-   AI 需要区分"任务优先级"和"建议执行顺序"。
-   用户明确指定的执行顺序优先于一般 AI
    建议，除非存在明显的依赖冲突或时间冲突，此时应说明原因。

**验收标准：** 1. 系统能生成有明确顺序的 Daily Plan。 2.
每项推荐任务都能展示简短推荐理由。 3. 计划考虑截止时间和任务依赖。 4.
用户可调整、锁定和撤销计划变更。 5. 计划不会仅按任务简单程度排序。 6. AI
不会无故改变用户确认的计划。

## 6.3 模块 C：Task Workspace（任务工作空间）

**需求优先级：P0**

每个 Todo 都拥有独立详情页，形成可持续积累的工作空间。

### C-01 任务基础信息

字段包括： - 标题。 - 描述。 - 所属 Project。 - 状态。 - 截止时间。 -
预计耗时。 - 实际耗时。 - 任务复杂度。 - 精力需求。 - 依赖任务。 -
完成标准。 - 下一步行动。 - 创建时间、更新时间和完成时间。

### C-02 Notes（笔记）

用途：保存任务相关的持续性信息、想法和参考资料。

支持： - Markdown 编辑。 - 文本笔记。 - 语音转文字。 -
图片、文件和链接附件。 - AI 总结与整理建议。

Notes 可编辑和更新。系统应保留必要的更新时间和版本信息，避免 AI
覆盖用户原始内容。

### C-03 Work Log（工作日志）

用途：记录每次实际工作过程。

每条记录至少包括： - 记录时间。 - 关联任务。 - 本次工作内容。 -
进度或发现。 - 遇到的问题。 - 下一步行动（可选）。 -
输入来源（语音或文字）。 - 关联 Focus Session（如有）。

Work Log 默认采用追加模式，不覆盖历史记录。

### C-04 Results（成果）

用途：保存任务最终产出或阶段性交付物。

支持： - 文字结果。 - 文件。 - 图片。 - 网页链接。 - 其他附件。

成果可标记为阶段性或最终成果。

### C-05 Reflection（复盘）

用途：保存任务完成后的经验和问题。

建议字段： - 实际耗时。 - 最终结果。 - 主要困难。 - 经验总结。 -
下次可改进之处。 - 后续行动。

### C-06 Task Memory（任务上下文恢复）

AI 可以在用户打开任务时，根据授权读取 Objective、Notes、Work
Logs、Results 和历史状态，生成上下文摘要。

摘要至少回答： 1. 上次完成了什么？ 2. 目前还剩什么？ 3.
有哪些未解决问题？ 4. 建议从哪一步继续？

用户可以查看摘要所依据的历史记录，并纠正 AI 的错误理解。

### C-07 任务详情页交互

建议采用分区或 Tab： - Overview - Notes - Work Log - Results -
Reflection

移动端优先保证快速浏览和快速记录，避免页面过深。

**验收标准：** 1. 一个任务可以关联多条 Notes、Work Logs 和 Results。 2.
Work Log 按时间顺序展示。 3. 任务完成后仍可查看历史资料。 4. AI
能基于历史记录生成任务恢复摘要。 5. 用户笔记和成果不会被 AI
自动覆盖或删除。

## 6.5 模块 E：Daily Review（每日复盘）

**需求优先级：P0**

### E-01 复盘入口

用户主动打开 Review 页面并开始语音或文字复盘。后续可提供可配置的提醒。

### E-02 语音复盘识别

AI 从用户表达中识别： - 明确完成的任务。 - 进行中的任务。 -
未完成的任务。 - 阻塞因素。 - 新增任务。 - 工作成果。 -
用户对当天工作的反思。

### E-03 任务状态建议

  状态          含义       AI 处理
  ------------- ---------- --------------------
  Inbox         尚未整理   保留待整理
  Todo          待执行     保持待执行
  In Progress   正在执行   更新进度
  Blocked       存在阻塞   记录阻塞原因
  Done          已完成     记录完成时间和成果
  Deferred      主动推迟   重新安排
  Archived      已归档     不进入日常计划

### E-04 状态变更规则

-   用户明确表示完成时，AI 可提出 Done 更新。
-   用户表示只完成一部分时，更新为 In Progress。
-   用户提到无法继续的原因时，可建议 Blocked。
-   用户明确要求延期时，可建议 Deferred。
-   用户未提及某任务，不代表任务已经完成。
-   语义存在歧义时，必须询问用户。
-   任何状态变更都应可撤销并保留变更记录。

### E-05 明日计划

根据未完成任务、依赖、截止时间、任务进度和用户可用时间生成计划草稿。用户确认后，写入下一日
Daily Plan。

### E-06 复盘报告

展示： - 今日完成事项。 - 今日新增成果。 - 进行中事项。 - 阻塞因素。 -
新增任务。 - 明日建议。

复盘应轻量化，目标是让用户通常能在 1--3
分钟内完成，不应增加额外管理负担。

**验收标准：** 1. 用户可以通过语音完成复盘。 2. AI
能区分完成、部分完成、阻塞和延期。 3. 未提及的任务不会被自动标记为完成。
4. 用户确认后才正式提交有歧义的状态变更。 5.
用户可以查看和撤销复盘引起的任务修改。 6. 明日计划生成后可编辑和确认。

# 7. 核心用户流程

## 7.1 购买与首次启动

1.  用户通过应用市场购买 Jarvis ToDo。
2.  应用验证购买凭证。
3.  验证成功后解锁永久基础功能。
4.  用户进入 Today 页面。
5.  用户可以先使用基础功能。
6.  用户可选择开始托管 AI 体验，或配置自己的 API Key。
7.  若用户选择托管 AI，首次成功调用时开始 72 小时计时。

## 7.2 语音创建任务

1.  用户点击全局语音入口。
2.  系统开始录音并展示状态。
3.  用户结束录音。
4.  ASR 生成转写文本。
5.  AI 判断意图并提取结构化任务。
6.  系统展示任务草稿和不确定字段。
7.  用户编辑或确认。
8.  任务保存到 Inbox 或指定 Project。
9.  AI 可建议是否拆解或加入 Daily Plan。

## 7.3 生成每日 Flow Plan

1.  用户进入 Today。
2.  系统读取已确认任务、依赖关系和截止时间。
3.  用户可填写当前精力和可用时间。
4.  Flow Engine 生成任务顺序和阶段。
5.  AI 展示推荐理由。
6.  用户确认或调整。
7.  Daily Plan 保存。
8.  后续调整需要展示变更原因。

## 7.4 恢复历史任务

1.  用户打开一个 In Progress 任务。
2.  系统读取任务历史上下文。
3.  AI 生成上次进度摘要。
4.  用户查看历史记录。
5.  用户选择继续建议的下一步，或自行修改。
6.  用户开始 Focus Session。

## 7.5 任务进度记录

1.  用户打开 Task Detail。
2.  点击 Add Note 或 Log Progress。
3.  通过语音或文字输入。
4.  AI 根据当前页面上下文判断记录类型。
5.  系统生成记录草稿。
6.  用户确认。
7.  记录保存到对应任务。

## 7.6 晚间复盘

1.  用户打开 Review。
2.  开始语音或文字复盘。
3.  AI 生成复盘摘要。
4.  展示任务状态变更建议。
5.  用户确认或修改。
6.  系统保存 Work Log、Results 和 Reflection。
7.  AI 生成次日计划草稿。
8.  用户确认后写入 Daily Plan。

## 7.7 BYOK 配置

1.  用户进入 Settings → AI Provider。
2.  选择 Provider。
3.  输入 API Key、Base URL 和 Model ID。
4.  点击 Test Connection。
5.  系统发送最小化测试请求。
6.  测试成功后启用 Provider。
7.  后续 AI 请求直接使用用户配置。
8.  用户可以随时切换或删除配置。

## 7.8 托管 AI 体验结束

1.  72 小时到期或额度提前耗尽。
2.  托管 AI 请求停止。
3.  应用显示体验结束说明。
4.  用户可以配置 BYOK。
5.  用户也可以关闭提示，继续使用基础功能。
6.  所有任务、笔记、日志和成果保持可用。

------------------------------------------------------------------------

  Capture Agent     意图识别和任务提取   语音转写、文字             结构化任务草稿

  Task Planning     任务拆解和依赖分析   任务、项目目标             子任务、依赖、下一步
  Agent                                                             

  Flow Agent        任务顺序建议         任务、用户状态、可用时间   Daily Plan

  Task Memory Agent 历史上下文恢复       Notes、Work Logs、Results  任务摘要和下一步建议

  Reflection Agent  每日复盘             语音转写、任务历史         状态建议、复盘摘要、次日计划
  ------------------------------------------------------------------------------------------------

## 8.2 AI 与规则引擎的职责边界

**LLM 负责：** - 自然语言理解。 - 意图分类。 - 任务拆解。 - 内容总结。 -
推荐理由生成。 - 模糊信息识别。 - 复盘内容提取。

**规则引擎负责：** - 数据格式校验。 - 任务状态合法性。 - 依赖约束。 -
截止时间约束。 - 用户锁定计划的保护。 - 变更确认和撤销。 -
任务排序中的硬性约束。 - 托管 AI 体验状态和额度校验。

不建议第一版让 LLM 完全自由决定任务顺序或直接写入关键数据。

## 8.3 AI 请求路由

### Hosted AI 路由

客户端 → Jarvis API → 权益/额度校验 → AI Provider → 结构化结果 →
客户端。

要求： - Jarvis 服务端持有托管 AI 服务商密钥。 -
客户端不得包含服务端密钥。 -
服务端按用户和试用权益实施预算与频率限制。 -
不应将用户任务内容用于未披露的训练或其他目的。 - 明确展示数据处理政策。

### BYOK 路由

客户端 → 用户选择的 Provider Adapter → 第三方模型服务 → 结构化结果 →
客户端。

要求： - BYOK API Key 保存在设备安全存储。 - 不经过 Jarvis 自有 AI
代理。 - 不上传至 Jarvis 普通业务数据库。 -
用户清楚知道数据发送到哪个服务商。 - 服务商调用费用由用户承担。

## 8.4 AI 输出规范

AI 应优先返回结构化结果，并包含： - 识别出的意图。 - 结构化字段。 -
信息来源（用户明确提供 / AI 推断）。 - 置信度或不确定字段。 -
推荐理由。 - 需要用户确认的操作。

所有会改变用户数据的操作都应经过业务层校验。

## 8.5 AI 失败处理

-   AI 请求失败时保留原始输入。
-   结构化输出不符合 Schema 时进行有限次数修复或回退为文本草稿。
-   不确定的任务字段留空，不编造。
-   不允许 AI 失败导致已有任务、笔记或日志丢失。
-   用户可以跳过 AI，直接手动完成任务操作。
-   Provider 鉴权失败时提示检查 Key、模型和服务商配置。
-   额度不足时停止托管请求，不得静默产生额外费用。

# 11. 技术与平台要求

## 11.1 平台规划

目标平台为 iOS 和 HarmonyOS。核心业务逻辑、数据结构和 AI
接口尽量共享；平台系统能力分别适配。

## 11.2 技术选型原则

最终技术栈需经过技术验证，不在 PRD 阶段预设唯一框架。

重点验证： - 跨平台 UI 框架对目标鸿蒙版本的支持情况。 - iOS 和 HarmonyOS
的原生能力接入方式。 - Widget / 服务卡片交互能力。 -
语音录制、系统语音识别和云端 ASR 的可用性。 -
本地数据库、数据同步和冲突处理。 - 后台任务、通知和系统限制。 - Markdown
编辑器和附件管理。 - iOS Keychain 与 HarmonyOS 安全存储。 -
两端应用内购买、权益验证和退款处理。

若跨平台框架无法满足系统级能力，可采用共享业务层与双端原生适配的方案。

## 11.3 建议的逻辑架构

1.  **Mobile App：** 页面、交互、本地缓存。
2.  **Domain Layer：** 任务、项目、计划和复盘业务规则。
3.  **Local Persistence：** 本地数据库、附件和索引。
4.  **Purchase Adapter：** iOS 与 HarmonyOS 购买和权益验证适配。
5.  **AI Orchestration Layer：** 模型调用、Agent 工作流和结构化输出。
6.  **Hosted AI Gateway：** 仅处理 Jarvis
    托管试用请求、预算校验和服务端密钥。
7.  **Provider Adapter：** BYOK 服务商适配，客户端直接调用。
8.  **Platform Adapter：** iOS / HarmonyOS 系统能力适配。

## 11.4 本地优先与同步

V1 至少支持： - 离线查看已缓存任务。 - 离线创建和编辑任务。 - 离线编辑
Notes。 - 本地附件管理。 - 数据导出和备份。

V1 不强制提供 Jarvis
自有云同步。若后续增加云同步，应独立评估服务器、存储和维护成本，并明确是否收费。

## 11.5 隐私与安全

-   用户数据按账户隔离（若启用账户功能）。
-   网络传输使用加密连接。
-   敏感数据按风险等级加密存储。
-   语音录音默认不长期保留，具体保留策略需在设置中明确。
-   用户可删除语音转写、任务、笔记和附件。
-   用户可导出个人数据。
-   用户可申请删除账户及相关数据（若启用账户）。
-   不默认开启持续麦克风监听。
-   AI 只能访问完成当前功能所需且已授权的数据。
-   BYOK Key 不进入普通日志、分析或备份。
-   对 Hosted AI 和 BYOK 分别披露数据流向及第三方处理方。

# 15. 风险与待决策事项

## 15.1 Flow Scheduling 有效性

心流理论、注意力残留和任务切换研究可以为产品设计提供理论依据，但不能直接证明某个固定排序算法最优。

需要通过用户测试验证： - Warm-up 是否有助于用户开始工作？ -
任务上下文连续性是否能改善持续投入？ -
用户主动报告的精力状态是否有帮助？ - AI 是否能学习个体差异？ -
用户是否觉得推荐减少了决策负担？

第一版应使用可解释、可调整的规则，不宜过早建立复杂黑盒算法。

## 15.2 ¥3 买断的成本风险

低价买断意味着后续收入有限，因此： - 基础功能应尽可能本地化。 -
不应默认承担无限云存储和同步成本。 - Hosted AI
试用必须设置预算和频率限制。 - BYOK 应作为长期 AI 使用的主要方式。 -
服务端托管 AI 体验成本需要持续监控。

## 15.3 BYOK 的兼容性风险

不同服务商的 API 兼容程度不同。应建立 Provider Adapter
和兼容性测试矩阵，避免简单地把所有服务商当作完全一致的接口。

## 15.4 API Key 安全风险

客户端直接调用第三方 API
时，密钥仍存在设备端风险。应使用系统安全存储、最小化日志、明确风险披露，并允许用户随时删除
Key。

## 15.5 平台支付审核风险

应用买断、AI 试用权益、数字功能解锁和外部 API Key
使用方式可能涉及不同平台政策。上线前必须分别确认 iOS 和 HarmonyOS
的最新审核与支付要求。

## 15.6 AI 过度干预

AI
如果频繁调整计划，可能成为新的干扰源。应优先在用户主动规划、任务发生重要变化或每日复盘时提供建议，并允许用户关闭或调整主动建议。

## 15.7 记录负担

Notes、Work Log、Results 和 Reflection
都有价值，但不能让用户为了管理任务花费过多时间。应支持轻量记录，并允许
AI 生成草稿供用户确认。

# 16. MVP 发布标准（Release Criteria）

首个可发布版本至少满足：

1.  用户可以通过应用市场购买 Jarvis ToDo。
2.  购买成功后永久解锁基础功能。
3.  用户可以创建、编辑、完成和删除 Todo。
4.  用户可以创建 Project 并关联任务。
5.  用户可以语音或文字输入任务。
6.  AI 可以提取结构化任务并让用户确认。
7.  Today 页面可以展示基础 Flow Plan。
8.  AI 推荐任务有明确、可理解的理由。
9.  每个任务具有 Notes、Work Log 和 Results。
10. 用户可以查看历史任务记录。
11. 用户首次成功调用托管 AI 时开始 72 小时体验。
12. 托管 AI 体验有明确预算和频率限制。
13. 体验到期后不自动扣费，基础功能继续可用。
14. 用户可以配置自己的 API Key。
15. API Key 使用系统安全存储，不进入普通业务数据库和日志。
16. BYOK 请求不经过 Jarvis 自有 AI 代理。
17. 用户能清楚理解第三方模型服务商的费用和数据处理方式。
18. AI 服务不可用时，基础任务管理仍可使用。
19. 关键数据变更可追溯，用户数据不会被 AI 无确认地覆盖或删除。
20. 完成 iOS 目标设备的基础体验验证。
21. 完成 HarmonyOS 目标设备的基础体验验证。
22. 两端支付、试用权益和购买恢复流程通过对应平台审核验证。

# 17. 理论依据与研究方向

以下理论用于指导产品假设，不应被表述为已经验证 Jarvis 排序算法有效。

## 17.1 Flow Theory（心流理论）

关注清晰目标、即时反馈、挑战与技能匹配等条件。可用于设计任务清晰度、任务难度和反馈机制。

## 17.2 Attention Residue（注意力残留）

Leroy（2009）研究了任务切换后注意力仍停留在前一任务的现象。可用于支持减少无必要切换、保留任务上下文的设计。

## 17.3 Implementation Intentions（实施意图）

Gollwitzer 与 Sheeran
的研究方向强调将目标转化为具体的"如果......那么......"行动计划。可用于把抽象任务转化为明确的下一步行动。

## 17.4 Time Management Research（时间管理研究）

Aeon
等人的时间管理元分析可作为任务规划与时间管理价值的背景依据，但不能据此推断某种
AI 排序方式一定更优。

## 17.5 后续验证

正式开发 Flow Engine 前，应建立可测量的产品假设，并通过可用性测试、A/B
测试或纵向用户研究验证： - 推荐顺序是否降低开始任务所需时间。 -
推荐顺序是否提升用户主观心流体验。 -
上下文恢复是否降低重新进入任务的时间。 -
每日复盘是否提高任务状态准确性。 - AI 计划是否减少用户的任务管理负担。

# 18. 产品愿景

Jarvis ToDo 不应成为一个功能堆叠的 Todo
清单，也不应成为一个需要用户不断聊天才能使用的 AI 助手。

它应该做到：

-   用户想到事情时，可以立即记录。
-   用户不知道先做什么时，可以获得合理建议。
-   用户开始工作时，可以快速进入状态。
-   用户中断工作时，可以恢复上下文。
-   用户完成工作时，可以留下笔记和成果。
-   用户结束一天时，可以快速复盘并规划明天。
-   用户不需要为 AI 承担强制订阅，可以选择托管体验或自带 API Key。

**Jarvis ToDo --- Less Planning. More Flow.**

**¥3 一次购买，基础功能永久使用；AI 体验 3
天，之后由用户选择自己的模型与成本。**
